## Findings

### F1 — P1: Run queries fail once the global store exceeds 1,000 events

Applies to R09 and inherited by R10. In `web/projections.py`, `run_page` passes
the global high-water mark as the `read_events` limit (R09 line 191; R10 line
195). The existing store permits at most 1,000 rows per read. A real store with
1,001 valid events raises `ValueError: limit must be an integer in 1..1000`;
the API's generic exception handler converts this into an internal-error 500.
The Runs and Execution graph views therefore stop working at ordinary volume,
even when the selected project has very few runs.

Use bounded store reads/projections with a fixed snapshot bound; do not remove
the storage limit or truncate the run index. Add above-1,000 and representative
large-volume tests/baselines, including events belonging to other projects.

### F2 — P1: One SSE connection blocks the entire served application

Applies to R09 and inherited by R10. `web/serve.py` uses the single-threaded
default `wsgiref.make_server`. The stream occupies its only request handler for
the default 20-second idle interval. A real-socket reproduction with a shortened
one-second interval timed out a second health request after 150 ms while SSE was
open. The same server configuration is used by the shipped entrypoint.

Separately, `LocalApi.wsgi` exits `with self._gate` before the SSE iterable is
consumed (`web/app.py` lines 108–110). During the active stream, the gate reports
zero active requests. Adding unbounded request threads alone would therefore
leave live streams outside the concurrency limit.

Provide bounded concurrent serving and retain/release a request slot for the
entire streamed response, including disconnect/error cleanup. Test concurrent
SSE plus normal requests against the actual entrypoint, saturation, a slow
client and stream disconnect. A stdlib transport is acceptable only if it meets
these existing runtime bounds; selecting a framework is not itself a remedy.

### F3 — P1: Pagination and SSE can permanently miss existing events

Applies to R09 and inherited by R10. In `event_page`, type filtering removes
rows before computing the scan position and next cursor (`web/projections.py`
lines 133–154). With two nonmatching events followed by a matching third event,
`limit=2` returns no items and no next cursor despite the matching event at
sequence 3. The client is falsely told that traversal has ended.

The stream has a second failure: its cursor advances only from returned project
items (`web/app.py` lines 347–362), ignoring scanned foreign-project events.
With 100 foreign-project events followed by this project's event at sequence
101, actual SSE returns only the open/idle frames with `lastSequence: 0` and
never delivers event 101. Reconnecting from that value repeats the omission.

Separate verified scan progress from emitted item IDs, or implement bounded
project/type-scoped queries. Preserve scope and resumable delivery across empty
filtered pages. Add both fixtures and reconnect tests; do not advance directly
to a high-water mark in a way that skips unscanned matching events.

### F4 — P1: R10 never presents a recorded cancellation request

R10's `_observation` maps only `RunSnapshot.status` and ignores
`cancellation_requested` (`web/projections.py` lines 256–269). A legally folded
queued → started → cancel-requested history has `status=running` and
`cancellationRequested=true`, but the API returns `observation=running`.
The declared `cancel-requested` type/legend does not make the state reachable.

Expose recorded cancellation intent from the authoritative fold while retaining
unknown/lost and actual observed terminal state separately. Do not turn a
request into observed stop. Add reachable-state fixtures for running/unknown
cancellation and actual terminal acknowledgement; enum-membership tests alone
do not prove this acceptance requirement.

### F5 — P2: R10 Run details silently lose runs beyond the first 250 global events

`web/src/components/DataViews.tsx` `RunDetail` reads at most five global pages
of 50 items, then filters by Run ID and returns `nextCursor=null` and
`highWaterMark=0` (lines 92–104). In a real 251-event store, a Run first present
at sequence 251 appears in the Run index but this exact detail-selection
algorithm collects zero facts. There is no continuation to that Run's facts.

Query bounded Run/Attempt-scoped detail pages instead of the first global pages.
Keep the actual snapshot/cursor and distinguish an incomplete page from absent
facts. Add the above fixture and a Run with more facts than the render cap.

### F6 — P1 acceptance gap: Required R10 inspection and lineage views are missing

The API's event view returns IDs/types/times, without payload or artifact links.
The revision view lists digests but has no immutable spec/plan inspection. Run
details show event metadata only; logs/metric values, execution environment and
decision/dissent/authorization lineage cannot be inspected through their
required views. The artifact tab requires an already known digest, and titles
for copying event IDs do not resolve result-to-data/code/config/decision links.
The Environment tab shows API limits, rather than the execution environment.
An ordered list of Runs also omits workflow/task dependency edges.

These are explicit R10 deliverables, including read-only history, not newly
requested R11 mutation or R12 proposal work. Deliver bounded, scoped inspection
and resolvable lineage using the existing folds/contracts. Charting libraries
and React Flow are not required to do so; deferring a particular library does
not defer the required graph semantics or inspection behavior. Until then,
acceptance statements should describe this as a partial read-only scaffold.
