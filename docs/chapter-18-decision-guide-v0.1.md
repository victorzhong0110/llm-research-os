## 0. 先给结论

第 18 章的 15 项问题不是 15 个同等紧急的选择题。如果现在一次性“全部定死”，其中一些决定会因为没有真实运行证据而变成猜测；如果全部推迟，又会使第一批协议和代码反复返工。

正确做法是分三类：

1. **现在必须定方向**：许可证、Python 与依赖、模式权威关系、事件外壳、SQLite 基线、安全方法、动态循环的边界；
2. **先保留接口，到 M1/M2 用原型验证**：Worker 传输、插件隔离、本地模型接口、前端、模型自主权评测；
3. **现在不应选择具体产品**：首家 GPU 云、5TB 网盘接入方式。它们必须在实际使用前根据当时价格、网络、API 和服务条款复核。

## 1. 正式名称和开源许可证

### 1.1 这其实是两个问题

名称主要影响辨识度、搜索和商标风险；许可证影响其他人是否愿意使用、贡献、集成或把项目用于云服务。二者不应该绑在一次决定里。

### 1.2 名称选项

| 选项 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| N-A：现在使用描述性正式名 | 容易理解，立刻可建仓库 | 通常难搜索、难形成品牌，也可能撞名 | 不推荐现在定死 |
| N-B：现在创造品牌名 | 易传播，未来可形成独立身份 | 未做 GitHub、PyPI、域名和商标排查时风险高 | 暂不推荐 |
| N-C：保留工作名，公开 MVP 前再命名 | 不阻塞代码；可等产品形态清楚后命名 | 早期文档需要使用代号 | **推荐** |

**推荐：N-C。** 目前继续把“LLM Research OS”当作工作描述，而不是承诺它是正式品牌。公开仓库前再做候选名清单，并检查 GitHub 组织/仓库、PyPI 包、常见域名、搜索结果和主要司法辖区的商标冲突。代码中的 Python 包名也先使用可替换的内部名，避免品牌名散落在协议字段里。

### 1.3 许可证选项

| 选项 | 优点 | 缺点 | 更适合什么目标 |
|---|---|---|---|
| L-A：Apache-2.0 | 宽松；商业和学术集成都方便；包含明确的贡献者专利许可与专利诉讼终止条款 | 他人可以做闭源修改或托管服务而不回馈 | 希望尽快形成广泛生态 |
| L-B：MIT | 文本短、理解成本最低、兼容面广 | 没有 Apache-2.0 那样明确的专利授权结构 | 极简小工具或专利风险较低的库 |
| L-C：MPL-2.0 | 文件级弱 copyleft；修改 MPL 文件通常要开放，同时可以与其他开源或专有文件组合 | 合规比宽松许可证复杂；插件边界与文件边界可能影响设计讨论 | 希望下游回馈核心修改，但不采用强 copyleft |
| L-D：AGPL-3.0 | 对通过网络提供修改版服务的情形有更强的源码开放要求 | 企业和云平台的合规审查通常更重；会减少某些集成与贡献 | 防止闭源托管攫取是首要价值取向 |

Apache 2.0 的官方文本明确授予符合条件的贡献者专利许可；MPL 官方 FAQ 将其描述为“文件级”copyleft；MIT 则是非常简短的宽松授权。[Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0)、[MPL 2.0 FAQ](https://www.mozilla.org/MPL/2.0/FAQ/)、[MIT](https://opensource.org/license/MIT)、[AGPL-3.0](https://www.gnu.org/licenses/agpl-3.0.en.html)

**推荐：L-A，Apache-2.0。** 原因不是它“最开放”这么简单，而是我们的目标是独立协议、训练后端适配器、Worker 和研究工具生态。明确专利条款以及较低的集成摩擦，比强迫所有下游开放更符合当前“让任何人使用和参与”的目标。

如果你的真实价值排序是“宁愿少一些采用，也要尽量迫使托管修改回流”，那就应选择 AGPL-3.0；这不是技术优劣，而是治理选择。

初始贡献治理建议使用 DCO/提交签署，不急于要求 CLA。数据集、模型、用户笔记和第三方资料不因代码采用 Apache-2.0 而自动获得相同许可证。

**改动代价：高。** 有外部贡献者以后换许可证，往往需要取得相关权利人的同意。因此许可证应在首次公开接受贡献前确定。

**选择码：`1-LA`（推荐）、`1-LB`、`1-LC`、`1-LD`；名称默认 `1-NC`。**

## 2. Python 最低版本、依赖管理和发布方式

### 2.1 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| P-A：Python 3.12+、uv、`pyproject.toml` | 环境创建和锁定快；单一项目文件；对 Apple Silicon 友好；与当前 NeMo、ms-swift 推荐环境相交 | Ubuntu 22.04 等系统自带 Python 较旧，需要 uv 单独安装 3.12 |
| P-B：Python 3.11+、pip/venv/requirements | 兼容稍多旧环境，学习资料多 | 多个 requirements 文件容易漂移；3.11 的官方生命周期更短 |
| P-C：Conda/Mamba 为核心 | 对 CUDA、科学计算二进制依赖有经验优势 | 控制面本身会被较重环境管理绑定；Mac 与远程 Linux 锁定结果更复杂 |
| P-D：一切只在容器内 | 运行环境看似统一 | Apple Silicon 本地开发更慢；无法解决宿主 Docker 不提供 Apple GPU 的事实；贡献门槛高 |

截至核对日，Python 3.12 的官方安全支持计划到 2028-10；当前 NeMo Platform 支持 3.12/3.13，ms-swift 要求至少 3.10 且推荐 3.12，PyTorch 当前要求至少 3.10。[Python 版本状态](https://devguide.python.org/versions/)、[NeMo 支持矩阵](https://docs.nvidia.com/nemo-platform/documentation/reference/support-matrix)、[ms-swift 安装说明](https://swift.readthedocs.io/en/latest/GetStarted/SWIFT-installation.html)、[PyTorch 安装说明](https://pytorch.org/get-started/locally/)

uv 会自动锁定和同步项目，也能在 CI 中用 `--locked` 拒绝未更新锁文件；它还能导出 `requirements.txt`、标准 `pylock.toml` 和 CycloneDX SBOM。Python Packaging Authority 已把开发依赖组标准化为 `pyproject.toml` 中的 `[dependency-groups]`。[uv 锁定与同步](https://docs.astral.sh/uv/concepts/projects/sync/)、[PyPA Dependency Groups](https://packaging.python.org/en/latest/specifications/dependency-groups/)

### 2.2 推荐基线

**推荐 P-A：**

- 核心包声明 `requires-python = ">=3.12"`；
- CI 至少测试 3.12 与 3.13；3.14 先作为允许失败的前瞻测试；
- 使用 `pyproject.toml`、uv 和提交到 Git 的 `uv.lock`；
- 开发依赖使用标准 `[dependency-groups]`；
- 核心控制面不依赖 CUDA、ms-swift 或 NeMo；这些进入独立适配器/Worker 环境；
- M0 先提供 `uv run ...`；有稳定 CLI 后再构建标准 wheel，并在公开 MVP 时发布 PyPI；
- 发布构建后端选标准兼容、简单的后端即可，不把运行协议绑定给 uv。

这里最重要的架构决定不是 3.11 对 3.12，而是：**训练后端的复杂依赖不得污染控制面的依赖环境。** 即使某个训练后端只能使用另一 Python 版本，也应在它自己的 Worker/容器里运行。

**改动代价：中。** 在公开发布前降低最低版本容易；发布后再提高最低版本会影响用户。

**选择码：`2-PA`（推荐）、`2-PB`、`2-PC`、`2-PD`。**

## 3. JSON Schema、Pydantic 与 TypeScript 类型谁说了算

### 3.1 为什么“只能选一个文件说了算”不是好问题

它混合了三种不同权威：

- **编写权威**：开发者实际修改什么；
- **对外协议权威**：其他语言和第三方插件据什么兼容；
- **运行语义权威**：诸如预算、循环终止、状态转换等无法只靠字段类型表达的规则。

### 3.2 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| S-A：手写 JSON Schema 第一 | 语言中立、对外清楚 | Python 开发体验较慢；复杂联合类型和自定义校验会重复实现 |
| S-B：Pydantic 第一，其他全部生成 | M0 速度最快；校验和序列化体验好 | 若没有冻结契约与兼容测试，外部协议会被 Python 重构意外改变 |
| S-C：TypeScript 第一 | UI 开发顺畅 | 核心执行在 Python；运行时校验与 Python 模型会变成第二套 |
| S-D：Protobuf/专用 IDL 第一 | 跨语言代码生成和 RPC 强 | 对人类可编辑的 YAML/JSON、开放扩展字段和研究型配置较笨重；M0 过度设计 |
| S-E：分层权威 | 同时兼顾开发效率与外部稳定性 | 需要 CI 生成、差异检查和契约测试纪律 |

Pydantic 当前可以从模型生成符合 JSON Schema Draft 2020-12 与 OpenAPI 3.1 的模式。[Pydantic JSON Schema](https://pydantic.dev/docs/validation/latest/concepts/json_schema/)

### 3.3 推荐的分层权威

**推荐 S-E，具体规则如下：**

1. M0 中，Pydantic 模型是字段结构的**编写入口**；
2. CI 生成并提交版本化的 Draft 2020-12 JSON Schema；生成结果发生变化时必须作为协议差异审查；
3. 发布后的 JSON Schema 是第三方实现的**外部契约**；
4. TypeScript 类型从已提交的 JSON Schema 生成，禁止手工维护同名类型；
5. JSON Schema 无法表达的规则写入“规范性语义条款 + 正反例 + 跨语言一致性测试”；
6. 破坏兼容的改动必须升级协议版本，不能只升级 Python 包版本。

简化成一句话：**Pydantic 用来写，JSON Schema 用来承诺，契约测试用来判定。**

**改动代价：高。** 一旦第三方积木和 UI 依赖协议，权威关系再改变会制造难以诊断的漂移。

**选择码：`3-SE`（推荐）；若坚持单一来源，可选 `3-SA` 或 `3-SB`。**

## 4. `ResearchEvent` 是否兼容 CloudEvents

### 4.1 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| E-A：完全自定义 | 字段最少、短期最快 | 将来接消息总线、事件路由和通用观测工具时需转换 |
| E-B：完整采用 CloudEvents，包括传输绑定 | 互操作最强 | M0 会引入不需要的 HTTP/Kafka 等绑定约束 |
| E-C：采用兼容外壳，领域数据仍自有 | 保留互操作路径，不绑定传输 | 比完全自定义多几个字段与映射规则 |

CloudEvents 1.0 的必需上下文字段是 `id`、`source`、`specversion`、`type`；领域负载放在 `data` 中，`subject`、`time`、`dataschema` 等可选。规范也明确把事件格式和传输协议区分开。[CloudEvents 规范](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)

### 4.2 推荐

**推荐 E-C：**

- 外壳使用 `specversion=1.0`、`id`、`source`、`type`、`time`、`subject`、`dataschema`、`data`；
- `data` 承载版本化 `ResearchEvent` 领域负载；
- 大制品只放内容哈希与 URI，不塞入事件；
- M0 只承诺结构化 JSON 映射，不承诺 Kafka/AMQP/HTTP binary-mode；
- 内部仍保留 `sequence`、`causation_id`、`correlation_id` 等扩展属性；
- 敏感信息和密钥绝不放在可广泛记录的上下文字段中。

这给未来 OpenTelemetry、消息总线或外部审计留下路径，又不会让 M0 变成云原生消息项目。

**改动代价：中。** 事件一旦持久化，字段映射就会进入迁移和兼容历史。

**选择码：`4-EC`（推荐）、`4-EA`、`4-EB`。**

## 5. Worker 首个传输：HTTP/WebSocket 还是 gRPC

### 5.1 这其实包含四个问题

1. 控制面怎样派发任务；
2. Worker 怎样回报心跳、日志和状态；
3. 大文件怎样传输；
4. 一台位于 NAT/防火墙后的机器怎样建立连接。

把四者都塞进一个“WebSocket 或 gRPC”选择会产生错误架构。

### 5.2 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| W-A：HTTPS/JSON + Worker 主动轮询/长轮询 | 最容易调试；穿过常见代理和 NAT；Python/浏览器都容易；断线恢复语义清楚 | 实时性不如常驻双向流；需要设计租约和幂等 |
| W-B：单一 WebSocket | 双向实时、日志流直观 | 重连、消息确认、代理超时、背压和去重仍需自行设计；不能把“连接存在”当作任务事实 |
| W-C：gRPC | 强类型、代码生成、双向流、性能好；gRPC 原生支持一元与多种流式 RPC | 引入 Protobuf 第二套 IDL；浏览器和部分代理环境更复杂；对 M2 的任务频率没有必要 |
| W-D：消息代理（NATS/Kafka 等） | 多 Worker、高吞吐、解耦好 | 要部署和运维额外基础设施，超出单人 M0/M2 的需要 |

gRPC 的官方文档确认它默认以 Protobuf 定义服务，并支持一元、服务端流、客户端流与双向流 RPC。[gRPC 核心概念](https://grpc.io/docs/what-is-grpc/core-concepts/)

### 5.3 推荐

**推荐 W-A，且把实时展示与正确性分开：**

- Worker 只需主动发起出站 HTTPS；
- 通过长轮询领取带租约的任务；
- 通过普通 HTTP 上报心跳、状态、事件与取消确认；
- 任务命令带幂等键，服务端可以安全重放；
- 实时 UI 日志另用 SSE；确有双向低延迟需要时再增加 WebSocket；
- checkpoint/数据集等大文件走独立的分块或预签名制品通道；
- 首次连接远程自建机器可用 SSH/Tailscale/受控隧道完成网络引导，这不改变 Worker 语义协议。

关键原则：断开连接只能产生 `unknown/disconnected`，不能自动判定失败；取消也是一个可审计协议，不是“关掉 socket”。

如果以后出现数千 Worker、高频细粒度消息或多语言 SDK，再用同一语义协议增加 gRPC 传输，不需要改 `ResearchSpec`。

**决定时机：M2 前用两台机器的断网/重连实验确认。改动代价：中。**

**选择码：`5-WA`（推荐）、`5-WB`、`5-WC`、`5-WD`。**

## 6. SQLite 事件存储与制品索引

### 6.1 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| DB-A：只建普通业务表 | 查询简单 | 状态被覆盖后难以审计和重建；不符合已决定的追加事实源 |
| DB-B：只存事件 JSON | 写入模型简单，历史完整 | 每次查询都要回放；迁移、筛选和 UI 性能较差 |
| DB-C：追加事件 + 可重建投影 | 历史完整，同时查询方便；符合事件与看板分离 | 需要投影器和一致性测试 |

### 6.2 推荐最小模式

**推荐 DB-C。** M0 不需要十几张复杂业务表，但至少应有：

- `events`：追加写入的事实；包含全局序号、事件 ID、流 ID/版本、类型、发生/记录时间、因果/关联 ID、模式版本、JSON 负载与负载哈希；
- `artifacts`：制品 ID、SHA-256、字节数、媒体类型、存储 URI、状态、创建时间与元数据；
- `artifact_links`：制品与 Run、Attempt、Event、Spec revision 的关系；
- `spec_revisions`：不可变 ResearchSpec 修订及哈希；
- `runs`、`attempts`、`workers`：从事件更新的查询投影，而不是第二事实源；
- `schema_migrations`：明确数据库版本。

操作规则：

- SQLite 数据库只放本机 SSD，不放网盘或网络文件系统；
- 开启 foreign keys；
- 本地并发需要时使用 WAL；SQLite 官方明确说明 WAL 不能跨网络文件系统主机工作；
- 文件内容放制品目录，按哈希寻址，数据库只存索引；
- 测试必须能从 `events` 重建投影并比对结果；
- 事件负载不允许静默原地修改，纠正通过新事件表达。

SQLite WAL 允许读写并发，但要求进程位于同一主机；foreign keys 需要应用显式启用。[SQLite WAL](https://sqlite.org/wal.html)、[SQLite Foreign Keys](https://sqlite.org/foreignkeys.html)、[SQLite JSON](https://sqlite.org/json1.html)

**改动代价：高。** 数据一旦积累，重做事件顺序、哈希和实体关系最昂贵。

**选择码：`6-DBC`（推荐）、`6-DBA`、`6-DBB`。**

## 7. 插件发现、签名、信任等级和隔离

### 7.1 先纠正一个危险假设

“插件有签名”不等于“插件安全”。签名只能帮助确认发布者和字节未被篡改；一个真实发布者仍可能写出恶意或脆弱插件。隔离、最小权限、能力声明、审批与审计仍然必需。

### 7.2 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| PL-A：所有 Python 插件进程内加载 | 开发最简单、性能最好；PyPA entry points 可标准发现 | 插件获得控制面完整进程权限；一次崩溃可拖垮系统 |
| PL-B：所有插件都放 OCI 容器 | 隔离边界清楚，适合训练后端 | 本地 Mac 开发重；简单格式转换也要启动容器；容器本身不是绝对安全边界 |
| PL-C：WebAssembly 插件 | 可移植、能力约束潜力好 | Python/CUDA/训练框架生态不适合整体迁入 WASM |
| PL-D：按风险分层 | 成本与隔离匹配；可逐步增强 | 协议和测试矩阵更多 |

PyPA 官方列出命名约定、namespace package 和 package metadata/entry points 三种发现方式，其中 entry points 能通过标准包元数据声明插件。[PyPA 插件发现](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)

### 7.3 推荐分层

**推荐 PL-D：**

| 等级 | 例子 | 执行方式 | 默认权限 |
|---|---|---|---|
| T0 内置可信 | 核心验证器、内置投影 | 同进程 | 仅声明的内部能力 |
| T1 已安装可信 | 由用户明确安装并审查的轻量插件 | Python entry point，同进程或受监督子进程 | 不自动读取密钥/任意文件 |
| T2 社区未知 | 笔记解析、模型供应商适配器 | 独立子进程，JSON-RPC/stdio | 临时目录、有限网络、显式 secret scope |
| T3 高风险执行 | 训练后端、任意代码、GPU 作业 | OCI 容器或远程 Worker | 能力令牌、资源/网络/费用上限 |

再增加以下规则：

- 每个 `BlockManifest` 声明网络、文件、GPU、secret、子进程、预算等能力；
- 安装和运行是两个审批动作；
- “skill/研究笔记”默认是**不可信数据**，不能因为它建议执行命令就获得插件权限；
- M0/M1 先做哈希固定和来源记录；公开社区插件市场前再加 Sigstore/cosign 验证；
- 签名身份、内容哈希、依赖 SBOM 和实际授予权限都写入事件；
- 核心策略、费用上限和审计写入不可被插件替换。

Sigstore/cosign 支持以密钥或 OIDC 身份验证制品/容器签名，并校验镜像摘要；OCI 也有标准镜像规范。[Sigstore 验证](https://docs.sigstore.dev/cosign/verifying/verify/)、[OCI Image Spec](https://specs.opencontainers.org/image-spec/)

**决定时机：现在定等级；M1 实现 T0/T1/T2；M2 实现 T3。改动代价：高。**

**选择码：`7-PLD`（推荐）、`7-PLA`、`7-PLB`、`7-PLC`。**

## 8. 本地模型统一接口与能力协商

### 8.1 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| M-A：核心只接受 OpenAI 兼容 API | 上手快；大量本地服务器和云 API 可接 | “兼容”并不代表工具调用、结构化输出、logprobs 等能力完全一致 |
| M-B：把 LiteLLM 作为核心抽象 | 供应商覆盖广、已有路由能力 | 核心命运与一个第三方聚合层耦合；仍需处理供应商差异 |
| M-C：自有最小接口 + 多个适配器 | 核心独立；能显式表达能力与降级 | 初期需要写少量适配代码和一致性测试 |
| M-D：每个模型原生 SDK 直连 | 能使用供应商全部特性 | 核心充满条件分支，很快失控 |

MLX-LM、llama.cpp 和 vLLM 都提供 OpenAI 风格或兼容端点，因此它是很好的首个适配器，而不是足够完整的内部抽象。MLX-LM 还明确警告其服务器只做基础安全检查，不建议直接用于生产。[MLX-LM Server](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md)、[llama.cpp Server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)、[vLLM OpenAI-Compatible Server](https://docs.vllm.ai/en/latest/serving/openai_compatible_server/)

### 8.2 推荐

**推荐 M-C：** 定义很小的 `ModelProvider`，包含：

- `generate()` / 流式生成；
- 模型与端点身份；
- 上下文长度和最大输出；
- 结构化 JSON/JSON Schema 能力；
- 工具调用、图像、embedding、logprobs、seed 等能力；
- 本地/远程、费用是否已知、数据是否离开本机；
- 超时、取消和重试语义。

能力协商不能只相信供应商声明：连接时做无害探测，并记录“声明能力、实测能力、当前策略允许能力”。缺失能力应产生明确降级或拒绝，不能静默模拟。

第一批适配器：

1. 确定性 Mock；
2. OpenAI-compatible HTTP；
3. Apple Silicon 上的 MLX-LM 或 llama.cpp 启动辅助；
4. LiteLLM 作为可选网关适配器，而不是核心依赖。

**改动代价：中。** 只要上层不直接使用供应商返回对象，更换适配器并不困难。

**选择码：`8-MC`（推荐）、`8-MA`、`8-MB`、`8-MD`。**

## 9. 前端技术栈与流程编辑器

### 9.1 选项

| 选项 | 优点 | 缺点 |

| UI-B：Vue + TypeScript + Vite + Vue Flow | 模板直观，Vue 学习体验友好；Vue Flow 功能完整 | 面向工作流编辑器的现成案例和生态相对少一些 |

React Flow 是 MIT 许可的节点编辑器组件，内置拖拽、缩放、多选、增删节点，并提供自定义节点、子流程、验证、保存恢复和 TypeScript 支持；Vue Flow 也是可行替代。[React Flow](https://reactflow.dev/)、[Vue Flow](https://vueflow.dev/guide/getting-started.html)

### 9.2 推荐

**推荐 UI-A，但按顺序建设：**

1. M1 先做只读 Run/事件/指标/血缘看板；

3. 最后加入 React Flow 可编辑画布；
4. 图形、YAML 和 Python 必须编辑同一 ResearchSpec，不得出现“画布专用隐藏状态”；
5. 后端负责最终验证，前端验证只用于即时反馈；
6. 不采用 Next.js 作为初始必要条件，静态 Vite 应用配 Python API 足够。

“先看后改”能让事件和状态语义先被真实数据检验，避免漂亮画布反过来绑架协议。

**决定时机：M1。改动代价：中低，前提是 API 和 ResearchSpec 不绑定 UI。**

## 10. 任意第三方云 GPU 与首个预算验证

### 10.1 “任意云 GPU”应改写成什么

字面上的“任意”无法保证：一台机器可能没有可用驱动、没有出站网络、不能运行容器、没有足够磁盘，或用户没有安装权限。

可验证的目标应是：

> 任何满足 Worker 能力契约的远程 Linux 机器，无论来自云厂商、GPU 市场、学校集群或开发者自建服务器，都能接入；厂商的创建、停止和计费 API 只是可选适配器。

### 10.2 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| G-A：先绑定 AWS/GCP/阿里云 | 企业能力完整 | 账户、IAM、网络和费用复杂；不符合低预算和任意机器目标 |
| G-B：先做通用 SSH/反向连接 Worker | 最独立；自建机和任意租赁机都能用 | 创建/销毁机器先由人手工完成 |
| G-C：把 SkyPilot 当核心供应层 | 已支持多云与现有机器，省适配工作 | 项目会在关键路径依赖另一编排器；其能力模型未必等于 ResearchSpec |
| G-D：直接做多家厂商 API | 自动化体验好 | 在协议未验证前维护成本过高；价格/API 会变 |

### 10.3 推荐路径

**推荐 G-B，然后增加可选 G-D：**

1. M2 的第一个真实闭环由用户手工租一台可 SSH 的 GPU 机器；
2. 安装通用 Worker，完成能力上报、训练、停止、失联、恢复和制品回传；
3. 证明核心不含厂商字段后，再实现一家自动供应商适配器；
4. 首家自动适配器暂倾向 RunPod；Vast.ai 作为低价市场型第二候选；SkyPilot 可作为可选供应插件，不作为核心。

RunPod Pods 按秒计费并提供 API，但官方要求在部署时到控制台查看最新 GPU 价格，且停止后的持久卷仍可能计费；Vast.ai 的 API 可搜索报价、可靠性和可租状态，也支持按报价创建 SSH 实例，但市场机器的异质性更高。[RunPod 定价](https://docs.runpod.io/pods/pricing)、[RunPod Pod API](https://docs.runpod.io/api-reference/pods/POST/pods)、[Vast.ai 创建实例 API](https://docs.vast.ai/api-reference/creating-instances-with-api)、[SkyPilot 现有机器](https://docs.skypilot.co/en/v0.10.0/reservations/existing-machines.html)

### 10.4 建议的首次预算验证

没有你的单次明确批准，不产生任何费用。到 M2 时建议：

- 先用 SimulatedRuntime 验证费用计算与停止逻辑；
- 再做只启动/上报/停止的 5–10 分钟 smoke test；
- 首次真实训练只用可随时终止的极小模型和数据；
- 单次硬上限建议不超过人民币 30 元；
- 整个 M2 的初始云验证累计建议不超过人民币 100 元，超出时重新向你说明证据与收益；
- 同时设置时间、费用、磁盘与失败重试上限；
- 自动充值、长期预付、Savings Plan 和不可退款承诺始终禁止由 AI 决定。

这些是建议的安全上限，不是已经获得的消费授权。

**决定时机：通用 Worker 现在定方向；供应商和真实价格在 M2 当天复核。改动代价：低，只要厂商适配器在核心之外。**

**选择码：`10-GB`（推荐）；自动供应商先记为 `10-RUNPOD-PROVISIONAL`。**

## 11. 5TB 网盘的归档接口

### 11.1 现在不能完成这个决定

我们还不知道网盘供应商、账户套餐和是否提供 API。仅知道“5TB”无法判断它是否支持 S3、WebDAV、官方 API、rclone，或者只有桌面同步客户端。

### 11.2 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A-A：原生 S3/对象存储接口 | 校验和、分块、生命周期和服务端操作较成熟 | 消费级网盘不一定提供 |
| A-B：WebDAV/官方 API | 比较通用，可自动化 | 限流、超时和大文件语义因供应商而异 |
| A-C：rclone 适配层 | 支持大量云盘、S3 与 WebDAV，可校验、断点续传、加密 | 又多一项外部工具；并非每个后端能力一致 |
| A-D：桌面同步目录 | 配置最少 | 冲突、占位文件、选择性同步与状态判断不适合自动化制品库 |

rclone 官方列出 70 多种存储与标准协议，支持校验、可恢复传输、加密包装与 API，因此很适合作为“冷归档边界”，而不是数据库或热训练盘。[rclone](https://rclone.org/)、[rclone crypt](https://rclone.org/crypt/)

### 11.3 推荐

**暂定 A-C：**

- M0 只使用本地制品目录；
- 等你提供网盘名称后，检查官方 API、rclone 后端、单文件限制、限流、版本历史和服务条款；
- 归档包先在本地生成 manifest、SHA-256 和可选客户端加密，再上传；
- 上传后做独立校验与抽样恢复测试；
- SQLite、运行中的 checkpoint、缓存和频繁写入日志永远不直接放网盘；
- 归档失败不能影响 Run 的事实记录，只产生待重试的归档状态。

**决定时机：需要归档前。改动代价：低。**

**选择码：`11-DEFER`（推荐）；获得供应商信息后再选 A/B/C/D。**

## 12. 公开发布前的安全威胁模型

### 12.1 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| SEC-A：公开前再做 | 现在最省时间 | 关键边界会已经固化；修复成本最高；可能在开发期泄露密钥或误花费用 |
| SEC-B：M0 做轻量活文档，按里程碑设门 | 与架构同步；单人项目可承受 | 需要每次边界变化时更新 |
| SEC-C：一开始做完整形式化安全评估 | 覆盖全面 | 在没有实现和用户前成本过高，容易产生大量假精确结论 |

OWASP 建议在开发生命周期早期做威胁建模，先画数据流和信任边界，再识别威胁、评估风险、选择缓解措施并写安全测试。[OWASP Threat Modelling](https://owasp.org/www-project-security-culture/stable/6-Threat_Modelling/)

### 12.2 推荐

**推荐 SEC-B。** M0 的第一版只需回答：

- 保护什么：API 密钥、云凭据、研究资料、未发布代码、训练数据、模型权重、费用额度和审计历史；
- 信任谁：人类研究者、控制面、模型供应商、资料源、插件、Worker、容器、云 API、制品存储；
- 边界在哪里：浏览器/API、模型调用、资料导入、插件执行、远程 Worker、制品上传；
- 主要失效：提示注入诱导执行、恶意笔记、secret 泄漏、命令注入、插件/容器供应链、Worker 冒充或重放、制品篡改、超预算、错误取消、失联误判；
- 哪些控制与测试阻断它们。

安全门：

1. M0 合并任何 secret/任意进程执行功能前，完成轻量威胁模型；
2. M1 接外部 LLM 和资料搜索前，完成提示注入与数据外传测试；
3. M2 接远程 Worker/云凭据前，完成身份、重放、最小权限、停止与费用测试；
4. 接受不受信任社区插件或公开发布前，做一次完整安全审查。

初期策略引擎可先用普通、可测试的 Python 规则；当策略需要独立分发或多语言执行时再评估 OPA，避免 M0 过度引入基础设施。[OPA HTTP API 授权示例](https://www.openpolicyagent.org/docs/http-api-authorization)

**改动代价：越晚越高。**

**选择码：`12-SECB`（推荐）、`12-SECA`、`12-SECC`。**

## 13. ResearchSpec 中动态循环的最小可验证语义

### 13.1 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| LOOP-A：v0alpha1 只允许 DAG | 最容易验证、调度和可视化 | 不能自然表达“训练→评估→AI 修改→再训练”的研究循环 |
| LOOP-B：允许任意图回边 | 表达力最大 | 很难静态证明终止、费用上限、重试含义与恢复点；UI 和执行器复杂度陡增 |
| LOOP-C：显式的受限循环/控制积木 | 能表达研究迭代，同时可验证和计费 | 比纯 DAG 多一组状态与事件 |

成熟工作流系统把重试、循环和递归做成显式结构，并为重试提供次数、条件与退避等边界，而不是把任意图回边当作无条件自由。[Argo Workflows Retries](https://argo-workflows.readthedocs.io/en/release-4.1/retries/)、[Temporal Retry Patterns](https://docs.temporal.io/design-patterns/error-handling-patterns)

### 13.2 推荐的 `LoopBlock`

**推荐 LOOP-C：**

- 图的顶层仍然无环；循环是一个显式复合节点；
- `body` 指向一个子图；每次迭代产生新的不可变 attempt；
- 必填 `max_iterations`；
- 只要会调用付费/GPU 能力，还必须有 `max_wall_time` 和 `max_cost`；
- `until` 使用受限、无副作用表达式，只能读取声明的指标/状态；
- 每轮明确 `iteration_input`、`iteration_output` 和 checkpoint；
- 终止原因枚举：条件满足、次数、时间、费用、人类停止、策略拒绝、失败、unknown；
- AI 想改变循环体时创建新的 ResearchSpec revision，不在运行中静默改图；
- `retry` 与“研究迭代”是不同概念：重试尽量保持相同输入，研究迭代必须记录策略或数据的变化。

M0 只需要验证上述结构并由 SimulatedRuntime 产生事件；真正的 AI 动态循环可到 M1/M2 再执行。

**改动代价：高。** 任意回边一旦进入持久化协议，后续很难恢复确定性。

**选择码：`13-LOOPC`（推荐）、`13-LOOPA`、`13-LOOPB`。**

## 14. 研究资料的许可证与训练数据使用策略

### 14.1 这其实是至少四个问题

1. 系统能否读取资料并向研究者摘要；
2. 能否把资料切片后用于 RAG；
3. 能否把内容复制进训练数据；
4. 能否公开或再分发数据集、模型与输出。

“在 arXiv/GitHub 上公开可下载”不等于“允许训练或再分发”。arXiv 明确允许作者选择多种许可证；其自有的永久非独占许可证只给 arXiv 分发权并限制其他主体的再利用。Creative Commons 也强调各司法辖区对 AI 训练的版权分析不同，并给出 BY、SA、NC、ND 条件的保守遵循方式。[arXiv License Information](https://info.arxiv.org/help/license/index.html)、[Creative Commons：AI Training](https://creativecommons.org/using-cc-licensed-works-for-ai-training-2/)

### 14.2 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| R-A：全部由用户负责，平台只警告 | 开发最简单 | AI 很容易把未知权利材料混进训练集；审计和公开结果风险高 |
| R-B：保守的用途级权利策略 | 风险可控、可审计；适合公开项目 | 会阻止一部分“可能合法但尚未确认”的使用 |
| R-C：自动按司法辖区给出法律结论 | 用户体验理想化 | 平台无法可靠替代律师；法律变化和事实差异太大 |

### 14.3 推荐策略

**推荐 R-B。** 对每份资料记录：

- 来源 URI、作者/权利人、抓取时间、版本/commit、内容哈希；
- SPDX license expression 或 `LicenseRef-Unknown`；
- 获取方式与用户声明；
- 允许用途分别标记：`read`、`cite`、`index`、`rag`、`train`、`redistribute`；
- 署名、ShareAlike、NonCommercial、NoDerivatives 等条件；
- 审核者、审核时间、理由与适用司法辖区；
- 是否含个人信息、秘密、访问控制内容或其他非版权限制。

SPDX license expressions 可以用标准标识符及 `AND`、`OR`、`WITH` 等表达复合许可。[SPDX License Expressions](https://spdx.github.io/spdx-spec/v3.0.1/annexes/spdx-license-expressions/)

建议默认规则：

- 用户自有/明确授权、CC0/公有领域：可按声明用途进入训练候选；
- CC BY：保留来源和署名义务，训练及发布仍需结合具体使用审查；
- NC、SA：醒目标记并在不满足相应条件时阻止；
- ND：按 Creative Commons 的保守指南，默认不进入训练数据；
- arXiv 自有许可、无许可证、许可证不明：可以保存引用与元数据；全文阅读/RAG 取决于合法获得和本地政策；默认禁止复制进训练集和再分发；
- GitHub 仓库许可证不能自动推断仓库内每个外部数据集、论文 PDF 或模型权重的权利；
- 人类可以覆盖默认拒绝，但必须填写理由并留下事件；AI 不能自行把“未知”改成“允许”。

这是保守的工程治理默认值，不是对具体材料或司法辖区的法律意见。真实公开训练或发布大规模数据集前，应进行针对性法律审查。

**改动代价：高。** 来源丢失后通常无法可靠补回；混合数据训练后也很难“删除某一来源的影响”。

**选择码：`14-RB`（推荐）、`14-RA`；不建议 `14-RC`。**

## 15. 如何判断模型可获得更高自主权限

### 15.1 不应该问“多少 B 的模型可以到 L4”

模型参数量、品牌或排行榜分数不能证明它会遵守预算、识别提示注入、正确取消任务或在不确定时升级给人类。授权对象也不只是裸模型，而是：

> 模型版本 + 系统提示 + 工具集合 + 检索资料 + 适配器 + 策略 + 运行环境。

其中任何一项改变，都可能改变行为。

### 15.2 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| AU-A：按模型品牌/大小白名单 | 简单 | 与真实任务风险弱相关；本地小模型和新模型都可能被错误授权或拒绝 |
| AU-B：通过一次静态基准就升级 | 可量化 | 容易针对测试过拟合；不能覆盖工具、网络、预算和恢复行为 |
| AU-C：能力项 × 风险项的持续评测与逐级放权 | 能对应真实权限；允许小模型在窄任务中可靠工作 | 需要维护场景、回归测试和运行证据 |

NIST 的生成式 AI 风险管理资料强调在 AI 产品、服务和系统的设计、开发、使用与评估生命周期中管理可信与风险，而不是只依据一次模型分数。[NIST AI RMF Generative AI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)

### 15.3 推荐的晋级机制

**推荐 AU-C。** 权限按能力单独授予，例如“可读取公开资料”不推出“可运行 shell”，“可运行本地 mock”不推出“可花云 GPU 费用”。

每个模型配置至少评测：

1. 结构化输出和模式遵循；
2. 引用是否可追溯，能否区分资料内容与系统指令；
3. 是否能提出反对意见、识别冲突和承认未知；
4. 工具选择、参数、幂等、重试、取消和恢复；
5. 对提示注入、恶意笔记、伪造成功消息和数据投毒的抵抗；
6. 费用与时间估计、硬上限遵守和异常停止；
7. 是否会把失联误判为失败或成功；
8. 是否会泄露 secret、私有资料或跨项目数据；
9. 在多次运行、不同种子和边界样例下是否稳定；
10. 模型/提示/工具/策略升级后的回归结果。

建议阶梯：

| 阶段 | 允许行为 | 晋级证据 |
|---|---|---|
| L0 建议 | 只生成提案，不调用工具 | 格式、引用、异议和不确定性通过 |
| L1 影子 | 生成计划与工具调用，但不实际执行 | 与人工决定对比，硬约束零违规 |
| L2 沙箱 | 执行本地 mock/临时目录，无 secret、无费用 | 工具、取消、恢复和注入测试通过 |
| L3 Canary | 对明确能力做一次低风险、低预算真实操作 | 人工审核、成本和产物验证通过 |
| L4 有界委托 | 在时间、费用、网络、数据和工具白名单内自主循环 | 多轮稳定性与故障恢复达到门槛 |
| L5 广泛委托 | 未来保留；仍受不可绕过的核心策略约束 | 目前不设“自动毕业”，需新 ADR 与安全审查 |

硬安全规则（例如“不得超过费用上限”“不得读取未授权 secret”）应要求 100% 通过；质量类指标使用统计阈值和置信区间。即使模型通过评测，人类仍可降低其权限。研究者可以在审计后覆盖 AI 的建议，但覆盖行为必须记录；AI 的异议不被删除。

**改动代价：高。** 如果早期用一个全局 `autonomy_level` 代替能力权限，之后拆分会触及所有执行路径。

**选择码：`15-AUC`（推荐）、`15-AUA`、`15-AUB`。**
